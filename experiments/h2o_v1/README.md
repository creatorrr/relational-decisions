# H2O-Lightning local diagnostic

Test [h2oai/h2o-lightning-4b](https://huggingface.co/h2oai/h2o-lightning-4b)
at revision `672dc01ed37a516357cd3c7da777c96699d3f16c` on the same first eight
dev programs used in the question-isolation comparison. The user requested
this checkpoint in place of ezjev; no ezjev inference was run.

The scope is fixed before scoring: 96 proposition assessments and 42 queries,
with the original GLiNER request groups replayed. The world text, frozen
`binary-reports-v2` questions, yes/no order and descriptions, positive/negative
product mapping, and hard-mode symbolic engine are unchanged. No prompt or
temperature search is performed. Heldout stays sealed.

## Result

H2O gets **85/96 assessments correct (88.54%)**, with **0.8403 macro-F1**.
All supported (38), refuted (20), and unknown (20) cases are correct. It gets
7/18 contradictory cases right; the other eleven become supported (four) or
refuted (seven). The remaining failure is preserving conflicting evidence.

| Model, same eight programs | Assessment accuracy | Macro-F1 | Query probability MAE | Exact queries |
| --- | ---: | ---: | ---: | ---: |
| H2O-Lightning-4B, isolated native questions | **88.54%** | **0.8403** | **0.0147** | **40/42** |
| OpenDecision-Large, isolated question in text | 43.75% | 0.3846 | 0.1195 | 26/42 |
| OpenJev, isolated native questions | 39.58% | 0.3395 | 0.1170 | 28/42 |
| GLiNER 340M, shared questions | 30.21% | 0.2119 | 0.1197 | 25/42 |

Every H2O query output also matches the independent exact evaluator when given
H2O's predicted facts. The two ground-truth query errors therefore originate
in language grounding. This is a promising improvement on the diagnostic;
eight unbalanced dev programs do not establish heldout generalization or
isolate model size, training, architecture, native serialization, and precision.
The subset's majority-label accuracy is 39.58%.

The fresh run took **1,072.77 seconds (17.88 minutes)** including initialization,
with **7.39 GiB peak RSS**. The checkpoint has 4,539,265,536 parameters including
its unused vision components. This serial CPU adapter does not use shared-prefix
caching, and its latency does not measure the publisher's GPU serving stack.

Artifacts are `h2o-quick8.{metadata,metrics,resources}.json`,
`h2o-quick8.{predictions,traces}.jsonl`, and `probe.json`.
The [matched comparison](../question_isolation/quick-comparison.json) contains
all seven configurations and is regenerated by that directory's
`summarize_quick.py`. No full 48-program H2O run was performed.

Practical next experiment: recognize evidence in individual reports and combine
positive and negative evidence symbolically, to avoid asking the model to
preserve a contradiction across the complete record. That hypothesis remains
untested. No scheduler or prompt change is justified specifically by these
results; shared-prefix execution is a separate performance opportunity.

## Attention and the d1 comparison

Neither candidate has bidirectional **text** attention:

| Model | Text computation | Questions share attention? | Work performed here |
| --- | --- | --- | --- |
| H2O-Lightning-4B | Qwen3.5: 24 causal Gated DeltaNet layers and eight causal full-attention layers | No: one causal prompt per question | Local smoke test and eight-program diagnostic |
| LiquidAI/d1-3B | LFM hybrid: causal convolutions and causal attention, with a shared state trunk and separate question branches | No: sibling branches cannot see each other | Source inspection only |
| OpenJev / GLiNER | Bidirectional encoders | Natively possible when questions occupy the same sequence | Prior experiments; see their reports |

In d1's [pinned implementation](https://huggingface.co/LiquidAI/d1-3B/blob/051bcc464b01b9f92942b364d9586b0ef5912432/hybrid.py),
`causal_attention` uses `is_causal=True`; `_own` admits only earlier tokens
in the same branch. Each branch can also attend to the shared state. Its
`runner.py` explicitly describes the result as mathematically equivalent to
each row evaluated alone, subject to BF16 kernel differences. Shared-prefix
computation can save substantial work without mutual question attention.

H2O's [pinned shim](https://huggingface.co/h2oai/h2o-lightning-4b/blob/672dc01ed37a516357cd3c7da777c96699d3f16c/h2o_lightning_shim.py)
sends one completion per question. Transformers' Qwen3.5 text model creates a
causal mask for its full-attention layers. `full_attention` means dense
attention here; it does not mean an unmasked bidirectional encoder. Vision
attention is a separate issue and is not exercised by these text tasks.
`attention-inspection.json` preserves source hashes and supporting excerpts.

Our frontier scheduler can use either causal or bidirectional scorers. Joint
attention between questions would be a separate architectural property;
parallel calls alone do not provide it. These runs do not evaluate serialized
graph paths or a learned joint distribution over predicates.

## Local implementation

The experimental backend is `src/relational_decisions/h2o.py`. It imports the
reviewed, pinned shim's pure prompt and probability helpers without starting
a server. It uses native `choice` questions, so the published `noul` confidence
floor is inapplicable. The published text temperature is **0.8**.

The CPU has four cores of quota and a 16 GiB RAM limit. The backbone uses BF16,
Transformers 5.18.0 and PyTorch 2.14.1+cpu. This differs from the older encoders'
FP32 runtime; it is a practical system comparison, not a controlled parameter
count or architecture ablation. It is not an INT8 experiment.

Each question runs as one unpadded sequence, with caching disabled. We use the
Transformers PyTorch fallbacks for the causal convolution and Gated DeltaNet
operators, unwrapping their optional GPU-kernel decorators. SDPA still applies
causal attention. No masks or learned weights are changed.

The publisher requires FP32 head computation. We project the final hidden
state onto the two verified answer-label rows in FP32, then normalize at the
published temperature. The IDs are checked by appending ` A` and ` B` to the
actual prompt: each must add exactly one distinct token without changing its
prefix. Computing only these rows avoids allocating a full FP32 vocabulary
head; full-vocabulary log normalization cancels in the option softmax.

`probe.py` checks native chat-template equality, repeated-score equality, and
agreement with an independent full-vocabulary FP32 projection followed by the
publisher's `format_answer`. Observed maximum probability difference is
**1.98e-7**, and repeated logits are bitwise identical on this CPU. The smoke
test peaks at **8.55 GiB** RSS. GPU vLLM numerical parity is not claimed.

## Reproduce

From the repository root, in a fresh Python 3.12 environment:

```bash
pip install --extra-index-url https://download.pytorch.org/whl/cpu \
  -r experiments/h2o_v1/requirements.lock.txt
python experiments/h2o_v1/probe.py --output runs/h2o-probe.json
python experiments/question_isolation/run_quick.py --model h2o \
  --output runs/h2o-quick8
```

Output and cache directories must be new. The lock records the experiment's
installed runtime dependencies, excluding the unused `llm2jev` package left
from setup for the cancelled ezjev run. Model weights download from the pinned
revision and are not committed. No API key is required.

For a future full dev evaluation, the general CLI also accepts
`rd-bench --backend h2o --split dev --output runs/h2o-dev`. That full run is
outside this quick diagnostic.
